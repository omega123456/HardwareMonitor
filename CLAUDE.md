# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

HardwareMonitor is a cut-down, low-CPU replacement for the parts of exelban/Stats the owner uses, in the macOS 26 menu bar on Apple Silicon: five status items, one per metric, each ⌘-draggable on its own and shown or hidden from the right-click menu's "Show in Menu Bar" rows (at least one always stays shown) (CPU usage over hottest core °C; GPU usage over hottest °C; memory used % over a pressure bar; system draw W over battery power W (`B0AC` × `B0AV`), with a bolt badge while charging; disk free over total). A 300 ms hover or a left click (which toggles) opens one shared non-activating panel under that item (artifact layout B): CPU and GPU tiles with 2-minute sparklines, peaks, temperatures and (CPU) Super/Efficiency and Performance clocks; memory, disk and power tiles; the top 8 processes by CPU and by memory. Right-click / ⌃-click closes it and opens HardwareMonitor's own app menu. It is **read-only**: it never changes system state, has no settings window and sends no notifications. It is an `LSUIElement` menu bar agent (`local.hardwaremonitor`) for personal use: self-signed, not sandboxed, not notarized. It is a single SwiftPM executable target that uses system frameworks only (never SwiftUI) and links the system `libIOReport`, built with the Swift 6.3 Command Line Tools. The only dependency is swift-snapshot-testing, used by the test target alone; tests run with Xcode's toolchain via `scripts/test.sh`. `Package.swift` pins Swift language mode v5.

## Commands

```sh
swift build                                 # debug build (compile check)
swift run HardwareMonitor --self-test       # pure-logic checks; exits before any UI, non-zero on failure
./scripts/test.sh                           # snapshot + behaviour + reader tests + SelfTest (Tests/HardwareMonitorTests), offscreen; extra args go to swift test (--filter …)
./scripts/coverage.sh                       # test.sh with LLVM line coverage of Sources/HardwareMonitor (System.swift and SelfTest.swift excluded); fails below COVERAGE_MIN (default 90); COVERAGE_HTML=1 → .build/xcode/coverage/index.html
./scripts/build-app.sh                      # debug "HardwareMonitor Dev" build → sign → quit running copies (prod too) → install to ~/Applications → launch
./scripts/build-app.sh --log-events         # extra args are passed to the app
BUNDLE_ONLY=1 ./scripts/build-app.sh        # signed production bundle .build/HardwareMonitor.app, not installed (CI)
tail -f ~/Library/Logs/HardwareMonitor\ Dev/events.log
pkill -x HardwareMonitorDev; open /Applications/HardwareMonitor.app   # back to production
./scripts/release.sh                        # (owner runs it) bump Info.plist version, verify, commit, tag vX.Y.Z, push → .github/workflows/release.yml
```

- **Sandbox:** SwiftPM fails inside the Claude Code Bash sandbox. `.claude/settings.local.json` excludes `swift build`, `swift run`, `swift package`, `./scripts/build-app.sh`, `./scripts/test.sh` and `./scripts/coverage.sh`, but only when the command is exactly one of these. Don't pipe, chain or prefix them (`|`, `&&`, `cd … &&`). `BUNDLE_ONLY=1 ./scripts/build-app.sh` is not exempt (the env prefix): inside the sandbox it reports the signing identity as missing, so run it with the sandbox disabled. Manual checks that touch IOKit/SMC, sysctl or disk capacity also need the sandbox disabled (inside it `volumeAvailableCapacityForImportantUsage` returns 0 and `sysctl` is denied).
- **Two suites.** `--self-test` covers the pure logic and needs only the CLT. To add a logic check, add a `check(...)` in `Sources/HardwareMonitor/SelfTest.swift`. It counts failures explicitly, because `assert` is compiled out of release builds. `Tests/HardwareMonitorTests/SelfTests.swift` also runs it under `swift test`, so coverage counts it. `SelfTest.swift` itself is excluded from the coverage total.
- **Tests** (`Tests/HardwareMonitorTests`, Swift Testing + swift-snapshot-testing) never touch real hardware, the real desktop, the login item, real defaults or the network, and never wait for a timer in real time.
  - **Toolchain:** the library imports XCTest, which only Xcode ships. So `scripts/test.sh` runs `swift test` with `DEVELOPER_DIR` set to Xcode and its own `.build/xcode` scratch path. `xcode-select` stays on the CLT (6.3) for app builds. Xcode's license must be accepted (sudo), so the owner runs that.
  - **Seams (DD-11):** every direct system call goes through `System` (`System.swift`, R-10): sysctl, host statistics, the IOKit registry, the SMC struct call (key info, read, key at index), power sources and the adapter, the two event sources (memory-pressure dispatch source, power-source run-loop notification), the boot volume's resource values, the running-application name for a pid, the `pmgr` DVFS table bytes and IOReport (availability, subscribe, sample, delta as plain `IOReportChannel` values; the 12 functions are `@_silgen_name` declarations there, Get = +0 unmanaged, Copy/Create = +1). Its members only call and return plain values; readers decode, `Metrics` decides. `System.swift` is excluded from coverage. Everything else outside the app goes through a replaceable static: `Env` (workspace, distributed and default notification centres, defaults, terminate, the clock `now`, which also stamps EventLog lines, the one-shot scheduler `schedule`, the launch-time lock and display-sleep queries) in `App.swift`; `StatusItem.showsStatusItem/popUp/systemAppearance/panelClass/anchor/animate/monitorClicks`; `Processes.commands` (the `ps`/`top` command lines; tests point them at `/bin/sh` fixture scripts, so the real launcher is tested); `Style.appearanceOverride`; `LaunchAtLogin.service`; `EventLog.url`; and the `Updater` closures and `session`. Production never changes them. New code that reaches the system adds a `System` member (or a seam) and fakes it in `Harness` (`Fakes.swift`), which installs fresh fakes for every test.
  - **Time:** every timer goes through `Env.at`/`Env.after` (one-shot, tolerance 10 % of the wait capped at 5 s, common run-loop modes). The only exception is the production hourly update check. Tests move the fake clock with `h.advance(seconds)`, which fires due one-shots in order; `h.armed` lists the pending ones (to the microsecond).
  - **Harness:** `h.system` is a `StubSystem` (sysctl values, CPU ticks advanced by `tickStep` before each read, VM counts, the GPU's `PerformanceStatistics`, SMC keys as type + bytes with `#KEY` answered from them and enumeration in name order, power-source dictionaries, boot-volume values; panel only: `appNames`, `registry` "entry/key" table bytes, `ioReport` on/off, the delta `channels`, `onSample`) that counts `cpuReads`, `diskReads`, `sourceReads`, `infoFetches`, `valueFetches`, `propertyReads`, `nameLookups`, `registryReads`, `subscriptions`, `samples` and `deltas`; `h.pressureEvent()`/`h.powerEvent()` deliver the R-2 events; `h.launch()` runs `AppDelegate`; `h.snapshot()` is the snapshot after the launch tick and one more. Fixtures (`Fixture.normal`, `charging`, `heldConnected`, `memWarningGpuMissing`, `memCritical`, `cpuWarm`, `hotCPU`, `lowDisk`, `diskCritical`, `terabyte`, `lowDrawBattery`, `lowDrawConnected`, `gpuGaps`, `shortHistory`, `smcUnavailable`, `noBattery`) are the plan's fixtures as readable values, installed as raw stub values for an M5 Pro (its 18 CPU and 7 GPU keys, the `clocksM5` tables and channels) so the real readers decode them; each carries its `Spark` (the plan's history generator: `cpuSpark`/`gpuSpark.history(usage:)`). `Fixture.psText`/`topText` are the `procs` text, `Fixture.procs()` its first-refresh ranking, `Fixture.clocksM5`/`clocksM1` the clock fixtures. Also a fake workspace (`h.ws.contrast`, `solid` = Reduce Transparency, `still` = Reduce Motion), its own notification centres, a `local.hardwaremonitor.tests` defaults suite, a captured right-click menu (`h.popUps`), an offscreen panel window (`OffscreenPanel.shown`), the item/screen frames (`h.itemFrame`, `h.visibleFrame`), recorded fades (`h.animations`), the outside-click monitor (`h.clickOutside()`, `h.monitorInstalls`) and a temp `events.log`. Panel tests call the trackers directly (`item.itemTrackers[.cpu]!.entered()/exited()`, `item.panelTracker…`) and click a given item with `item.handle(event, on: .gpu)`; `h.itemFrame` is every item's frame, so move it to check that the panel follows. A ⌘-drag out is `item.visibilityChanged(g)` (items are always invisible in tests).
  - **Real processes:** `ps`/`top` are `/bin/sh` scripts written by `h.script(name, body)`; each run appends its pid to `<name>.pids` (`h.launches(name)`). Their output arrives in real time on the main queue, so tests `await h.until { … }` (polls, 5 s cap) while timers stay on the fake clock. A script that must die on terminate ends in `exec sleep 30` (a plain `sleep` child would keep the pipe open). Don't assume a script launched just before a close has logged its pid. Assert on behaviour through `h.log` (EventLog lines), the stub's counters, `h.armed` and the sampler's snapshot.
  - **Pitfalls:** never `performClick` (its tracking loop can end the run loop Swift Testing drains on, which exits the run silently with status 0); call `StatusItem.handle(_:)` with a synthetic event, or send the menu item's action. Keep the `AppDelegate` a test launches (`let app = h.launch()`): its sampler's timers hold it weakly, so a discarded delegate stops ticking. Don't let a test's sampler hold its StatusItem strongly (`sampler.onChange = { [weak item] in item?.update() }`). `NSMenu` only draws while tracking on a real display, so the menu is snapshotted as a text outline.
  - **Snapshots:** `SnapshotTests` renders the status image (`StatusImage.<case>.png`) by drawing `Glance.image()` (the production drawing-handler path) into a 2x bitmap over a fixed menu-bar backdrop, compared at `precision: 0.99, perceptualPrecision: 0.98`. Each case runs its fixture through the stub `System`, the readers and `Sampler`. The appearance is pinned through `Style.appearanceOverride`. The matrix is the plan's States table in dark and light (normal, charging, heldConnected, lowDrawBattery, memWarningGpuMissing, memCritical, cpuWarm, hotCPU, lowDisk, diskCritical, terabyte, smcUnavailable, noBattery, no DEV label), plus Increase Contrast for normal, memCritical and hotCPU (dark) and normal (light). The panel (`Panel.<case>.png`) is drawn by `PanelView.show` (the production path) at 2x over a flat wallpaper colour: the plan's Phase 2 panel matrix (12 fixtures dark and light; dark only gpuGaps, shortHistory, stale, smcUnavailable, noBattery, the process-list states, clocksM1/measuring/unavailable, both short-screen cases; Increase Contrast and Reduce Transparency for charging). `Panel.normal` (dark) is also the "procs loaded" and `clocksM5` case. `StatusImage.separateItems(Light)` draws the five one-column glances as `StatusItem` builds them (DEV on CPU). The right-click menu is `Menu.<case>.txt` (defaults, loginOnUpdatesOff, lastShown). To add a state, add a `Case`. System fonts and the one SF Symbol (disk) are inherent, so references are tied to the macOS version.
  - **Re-recording:** the first run of a new case records its PNG and reports a failure. Delete a PNG to re-record it, then always check the new image by eye against the offline artifact before committing.
  - **Coverage:** `scripts/coverage.sh` gates on 90 % lines of `Sources/HardwareMonitor` without `System.swift` and `SelfTest.swift`. What stays uncovered is the real call inside each `Env` seam, the CFUserNotification prompt and `main()`.
  - **CI:** tests aren't run there yet; the references were recorded on the owner's Mac and may differ on the `macos-26` runner.
- **Dev vs production (R-25):** production is `/Applications/HardwareMonitor.app` (`local.hardwaremonitor`, from the DMG, self-updating). `build-app.sh` builds **HardwareMonitor Dev**: a debug build with bundle ID `local.hardwaremonitor.dev` and executable `HardwareMonitorDev`, so UserDefaults and the login item are separate. `#if DEBUG` gates the dev behaviour: no updater, its own log folder (`HardwareMonitor Dev`), the "DEV" label drawn at the image's left edge and the disabled version row in the menu.
- **App icon:** `scripts/make-icon.swift` draws `Resources/AppIcon.icns` (Concept A, the five-bar meter; 3 bars at 32 px, 2 at 16 px). Build it inside the sandbox (`swiftc -module-cache-path "$TMPDIR/mc" scripts/make-icon.swift -o "$TMPDIR/make-icon"`), run `"$TMPDIR/make-icon"` from the repo root with the sandbox disabled (`iconutil` fails inside it). `build-app.sh` copies the icon into the bundle; `release.yml` also makes it the DMG volume icon.
- **Never run the binary directly** (`.build/.../HardwareMonitor`) for real use; launch the installed app with the script or `open ~/Applications/HardwareMonitor\ Dev.app`.
- `scripts/make-cert.sh` is interactive (keychain password, trust dialog). The owner runs it in Terminal.app, not you. It creates the "HardwareMonitor Local Signing" identity (DD-13), which the updater checks every download against. Its SHA-1 is pinned in `.github/workflows/release.yml` (upper and lower case).

## Architecture

All work runs on the main thread and is event-driven (DD-6). The data flows one way:

```
 NSWorkspace / distributed notifications     memory-pressure source · power-source notification     one-shot timers (Env)
 (sleep, displays, session, lock)                       │ (created through System)                   tick 1 s · disk 60 s
            │                                           ▼                                                    │
            └─────────►  Visibility gate  ──►  Sampler (Sampler.swift)  ◄────────────────────────────────────┘
                         (App.swift)            │ asks the per-source readers (decode; rules in Metrics):
                                                │   CPU · GPU · Memory · Thermal (SMC) · Power (SMC + power source) · Disk
                                                │            │
                                                │            ▼  every direct call
                                                │        System (System.swift) ── stubbed in tests, excluded from coverage
                                                ▼
                                                │   Processes (ps/top, off-main) · Frequency (IOReport)  ── panel open only, 1 s round
                                                ▼
                         Snapshot + PanelExtras (pure values, Metrics.swift; R-3a debounce + histories)
                                                │
                                                ▼
     Column model (Metrics.columns) ──► Glance · PanelContent (Metrics.panel: tiles, lists, labels) ──► Panel/PanelView (Render.swift)
                                                │
                                                ▼
          StatusItem.swift: one NSStatusItem per shown metric · appearance KVO · image-on-change · a11y label · clicks · right-click menu ·
                            hover panel (placement, fade, outside-click monitor) ── open/close ──► Sampler.panelOpened/Closed

 AppDelegate: wiring · visibility gate · redraw triggers · LaunchAtLogin · Updater · EventLog
```

Cross-cutting rules that need several files to see:

- **One seam for the system (R-10, DD-7, DD-11):** only `System` calls the OS. The per-source readers (`SMC`, `Thermal`, `CPU`, `GPU`, `Memory`, `Power`, `Disk`) decode its raw values; every decision rule lives in `Metrics.swift` as `static func`s and value types (visibility, chip and key tables, prefix filter, usage, memory, pressure, plausible maximum, power state, formats, levels, R-3a debounce, history, the column model, the accessibility summary) so `SelfTest` covers it without UI. **Escalation:** if a rule is missing or wrong, stop and report it to the owner; never put decision rules in view, StatusItem, Sampler or reader code.
- **Read only what is shown (owner, 2026-10-13):** `Metrics.needed(shown:panelOpen:)` is the shown items' metrics, or all of them while the panel is open. `Sampler` reads only those. The tick is armed only while CPU, GPU, Memory or Power is needed and the disk read only while Disk is. `Thermal.read(cpu:gpu:)` reads each key list only if asked, `PDTR` is read only while the panel is open, and the pressure and power events read nothing for a metric that isn't needed. A metric that stops being needed is forgotten (values, debounce, history) and shows "—" when needed again. A newly needed one is read at once. `StatusItem.setShown` stores the hidden items (`hiddenMetrics`) and calls `Sampler.show`.
- **One scheduler (DD-2, DD-4, NFR-1):** `Sampler` owns every data timer through `Env`: the 1 s tick (re-armed after each sample on a 1 s grid from when that tick was due, so lateness doesn't add up and battery power stays one SMC window behind `PSTR`, while needed), the 60 s disk read (while needed) and, only while the panel is open, the 1 s panel round (re-armed 1 s after each round *starts*), all one-shot. The other one-shots are the hover delays (300 ms open, 400 ms close), the 120 ms fade order-out and the 5 s process timeouts. Launch runs the power state, the disk and one tick at once (R-1). No repeating timers except the production hourly update check. No polling loops, no AX, no global event monitors except the outside-click one (only while the panel is open), no HID sensors.
- **Do the work once (DD-3, R-6, R-9):** at launch the SMC connection is opened, key info is fetched once per key and cached (misses too), the chip's key lists are resolved (keys the SMC lacks are dropped; on the M5 Pro `Tg1g`) and the IOAccelerator entry is kept. Per tick (each only while its metric is needed): every resolved temperature key (full lists; owner decision 2026-10-12: the NFR-1 idle cost is accepted as is, although the probe estimated ~0.29 % against the 0.25 % budget, so don't apply the plan's contingency), `PSTR`/`B0AC`/`B0AV` (`PDTR` only while the panel is open) and the one `PerformanceStatistics` property. The chip generation is the whole token `m<number>` (M10 is not M1); M4 Ultra uses the M4 Pro/Max GPU keys; an unknown chip enumerates the SMC once and filters `Tp*`/`Te*`/`Tg*` by name before any info or value fetch.
- **Events, not polling (R-2):** memory pressure and power-source changes re-read and redraw at once; the power-source state and adapter rating are read at launch, on those events and on every return to visible.
- **Visibility gate (R-21, NFR-2):** asleep, displays asleep, session resigned or screen locked pauses everything (timers cancelled, later events ignored, updater paused). Return: redraw from the last snapshot, clear both histories, re-read the power state, one tick and one disk read at once (which re-arm the cadence), resume the updater (a missed check runs). A launch while not visible starts paused.
- **Panel-only work (R-11, owner rule: zero cost while closed):** every open path calls `Sampler.panelOpened(rows:)` and every close path (pointer left, click, outside click, Space change, screen change, menu, leaving visible) `Sampler.panelClosed()`. A round runs `ps` (every round) and `top` (the second round, then every 6th: `Sampler.topRounds`) through `Processes` (off main, single flight each, 5 s timeout, results on main; skipped when the short-screen check left the tile out) and one IOReport sample through `Frequency` (the first after opening is the baseline: "Measuring…"; a window that started while `top` ran only re-baselines, because `top`'s ~2 s of kernel work holds a Super core at full clock). Close cancels the round, terminates running children, discards late output (run ids), forgets the ranked rows and drops the clock sample and `PanelExtras`. The first open in an app run reads the DVFS tables and creates the subscription (kept). Ranking (R-12 hysteresis), naming (≤ 16 lookups, only for rows shown) and clock maths live in `Metrics`.
- **Missing values (R-3a):** "—" before the first success; after a success a failed read keeps the last value until 3 consecutive failures; a missing CPU baseline keeps the value and stores a gap; failed reads store gaps.
- **Redraw only on change, drawn per appearance (DD-5, R-16):** `Glance` is a pure value of what the image shows (incl. the `Style`); the image and accessibility label are rebuilt and reassigned only when it changes. Redraw triggers: the button's effective appearance (KVO), accessibility display options, system colours, screen parameters (not GlanceBar's clock/time-zone/locale triggers).
- **Visuals (R-14, R-15, deviations 1, 2, 7, 9, 11):** glyphs are the artifact's `SYM` paths (13 pt in the bar, 14 pt in panel headers, 1.4-unit strokes scaled with the box) and the bolt its `BADGE` path; disk alone keeps the SF Symbol `internaldrive` (owner choice, 2026-10-12); fixed slots reserved at the widest realistic text including the critical `!` (an item's image never changes width; one item is its glyph, 3 pt and its slot, with no side padding because the menu bar spaces the items (owner, 2026-10-13); the five as one image measure 293 pt, Dev 328 pt with "DEV", which goes on the first shown item in default order; the earlier 294 pt was accepted by the owner on 2026-10-12, superseding the plan's ≤ 280 pt criterion, because the slots include the critical `!` and the artifact's 1.5 pt gaps); round, then switch units (`9.96 → 10W`, `999.6 G → 1.0T`); units 0.8 em regular at 78 % of the value's colour; warning amber semibold with no mark, critical red bold plus a heavy `!`; light warning text `#9A5A00`, fills `#C77700`; normal is neutral (no green); Increase Contrast draws dim text at full strength and a stronger track in the menu bar; the power bottom line is battery power (`B0AC` mA × `B0AV` mV, little-endian `si16`/`ui16`; not `PPBR`, which reads ~1 W while an M5 Pro charges at ~25 W: owner, 2026-10-13), signed (positive charging, negative draining), shown one read late because `PSTR` holds the previous ~1 s SMC window's draw (owner, 2026-10-13): the tick's 1 s grid keeps the two one window apart, fg whenever a battery exists, with a "−" while it drains (on battery, or connected while the load exceeds the charger; the slot is reserved at `−188W`: owner, 2026-10-13), a dim "—" only without a battery (deviation 3, DC-in, reversed by the owner on 2026-10-12 to match Stats; `PDTR` is read for the panel's "Adapter in" row only while it is open); GlanceBar's value baselines 10.4 / 19.4; the open-panel highlight is the system's status-button highlight (`button.highlight`, re-applied on every update and after a click's tracking), not drawn into the image (owner, 2026-10-13: the drawn 22 % grey pill needed the 4 pt padding).
- **Click model (DD-10):** no status item holds a permanent `menu`. The panel is shared and anchored to one item (`anchored`), which carries the system highlight (`isHighlighted` in tests) and sets the placement. A left click on the anchored item closes the panel, on another item moves it there, or opens it there when closed. Hovering another item while open moves it at once. Every item opens the same menu. Its "Show in Menu Bar" rows disable the last shown item, which also loses `.removalAllowed`. In production, a ⌘-drag out (KVO on `isVisible`) hides an item like its row, and `autosaveName = "metric.<name>"` keeps each item's position. Tests never set either, because they write the standard defaults. right-click/⌃-click closes the panel and pops up the menu built on open (it takes the system appearance, `StatusItem.systemAppearance`, not the menu bar's).
- **Panel (R-17–R-19, DD-9, DD-12):** GlanceBar's non-activating `.popUpMenu` panel without its per-column hot logic and without Esc. Layout B with the artifact's metrics (deviation 9): 368 pt box (354 content + 7), radius 12, no border, 8 pt gutters, tiles radius 6 / padding 8 (half tiles 173 pt; tiles in a row share its height), 679 pt tall with 8 rows (619 with 5, 477 without the lists, +23 with the stale footer). The short-screen row count (8 / 5 / left out) is decided at each open from `PanelView.height`. `Metrics.panel` builds `PanelContent` (tiles, lists, footer, every string and accessibility label); `PanelView` only draws it, one accessibility group per tile and per list. Panel tokens: dim 0.72/0.66 (Increase Contrast 0.92), track 0.16/0.10 (0.32/0.26), sep 0.12/0.10 (0.40), tile tint 0.07/0.045, background 0.94/0.97 (solid under Reduce Transparency, blur hidden); warning fills `#C77700` in light, text `#9A5A00`. Memory and disk critical values get a leading "! " like the temperature.
- Code comments cite "R-N", "NFR-N" and "DD-N". These refer to `.agent/plans/2026-10-12_hardwaremonitor_plan.md`, which holds the full spec, the wireframes, the owner's deviations from the artifact and the reasons behind the constants. The approved design is `.agent/plans/assets/2026-10-12_hardwaremonitor_plan-artifact.html`; where the plan's text and the artifact differ, the artifact wins except for the owner's deviations. Key tables, power key names and (later) the clock rule and process command lines come from exelban/Stats (MIT), credited in source comments.

## Architectural decisions (binding)

`.agent/adr/` is an append-only decision ledger, governed by `.agent/ADR_POLICY.md`. Never edit or delete an existing ADR. To reverse one, write a new ADR with a `## Relationship to previous decisions` section. The decisions below are recorded there (the plan's Notes list them); read the relevant ADR before you change:
- frameworks, the dependency policy or the test toolchain (AppKit only, no runtime packages, the system `libIOReport` linked, test-only swift-snapshot-testing on Xcode's toolchain)
- private interfaces and the system seam (IOReport through `@_silgen_name`, the SMC struct call, every direct system call behind the single `System` seam, which is excluded from coverage)
- data sources and cadence (SMC/host/IOKit on one 1 s tick, events for memory pressure and power, the visibility pause)
- panel-only work (Stats' `ps`/`top` and IOReport clocks, only while the panel is open)
- the signing identity ("HardwareMonitor Local Signing")
- the outside-click global monitor, only while the panel is open
- one status item per metric, with reads gated by the shown set (reverses the plan's single status item)

## Verifying behaviour

Acceptance criteria are tagged **[agent]** (builds, `--self-test`, tests, file contents, `codesign`/`plutil`/`otool` output, `--log-events` lines read from the log file) or **[owner]** (live UI, menu bar on light and dark displays, sleep/lock, Activity Monitor, `pmset`, VoiceOver, macOS settings, anything that needs hovering or clicking the real menu bar).

- The owner keeps using the desktop while agents work. HardwareMonitor is read-only; never write to the SMC or change system state.
- `open`, `pgrep`, `top`, `ps`, `screencapture` and `/usr/bin/log` need the sandbox disabled, which auto mode may deny; report such checks as not verified rather than forcing them.
